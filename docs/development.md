# Разработка

## Требования и структура

Нужен Mac с Apple Silicon и инструментами разработки Apple: `swift`, `xcrun`, macOS SDK, `codesign`, `plutil`; для тестов PoC — `/usr/bin/python3`. Пакет объявляет Swift tools 5.9 и macOS 13 как минимальную платформу, но для компиляции нужен SDK с API macOS 26 (`glassEffect`); проверенное окружение — Xcode 27.0 (27A266a), Apple Swift 6.4, macOS SDK 27.0. Объявленная версия tools не является подтверждённой минимальной версией компилятора. Скрипт выпуска собирает только ARM64. Внешних Swift-пакетов нет. Код Liquid Glass включается на macOS 26+, на более старых версиях используется системный материал.

- `Package.swift` — продукты, цели и тестовые зависимости.
- `Sources/` — ядро, платформенный слой, IPC, приложение и две службы; [архитектура](architecture.md).
- `Tests/` — Swift-тесты состояний, платформы, восстановления и UI.
- `Resources/` — Info.plist, шаблоны LaunchDaemons и исходные/готовые ресурсы иконки.
- `scripts/` — сборка, проверка bundle, тесты, установка и удаление служб.
- `poc/` — исходный исследовательский прототип и его тесты. Он не входит в `.app`.
- `docs/` — актуальные инструкции и статус испытаний.

## Проверки

Из корня проекта:

```sh
./scripts/test-safe.sh
```

Скрипт выбирает SDK через `xcrun`, выполняет `swift test`, `python3 -m unittest discover -s poc/tests`, `python3 -m unittest discover -s scripts/tests`, проверку синтаксиса `scripts/*.sh` и plist. Тесты используют подставные исполнители и временные файлы; процессные тесты запускают безвредные дочерние процессы. Системные службы и настройки питания не меняются.

Тесты оформления DMG требуют отдельного окружения упаковщика и временно подключают тестовый HFS+ образ:

```sh
./scripts/setup-dmg-tools.sh
.build/dmg-tools/bin/python3 -m unittest discover -s scripts/dmg-tests
```

Они проверяют настоящую разметку Finder и не запускают приложение или службы. При неудачном отключении тестовый образ сохраняется. Оба workflow выполняют эти проверки; обычный CI не сохраняет DMG.

Для отдельной проверки:

```sh
export SDKROOT="$(xcrun --sdk macosx --show-sdk-path)"
swift test
python3 -m unittest discover -s poc/tests
python3 -m unittest discover -s scripts/tests
bash -n poc/lid-test.sh
```

Сам `poc/lid-test.sh` — аппаратный эксперимент с привилегированными операциями, а не обычный тестовый runner. Не запускайте его как часть сборки или параллельно с приложением. Безопасный набор использует его функции с подменёнными системными операциями.

## CI и артефакты

Workflow [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) запускается на всех pull request, push в `main` и вручную через **Actions → CI → Run workflow** (после попадания workflow в `main`). Одна проверка **Build and test (macOS ARM64)** выполняет:

1. Проверку архитектуры и вывод версий Xcode, Swift, SDK и Python.
2. `scripts/test-safe.sh`: Swift- и Python-тесты, синтаксис скриптов и plist; дополнительно `bash -n poc/lid-test.sh`.
3. `scripts/build-app.sh`: release ARM64, ad-hoc подписи и проверку установочного содержимого.
4. `--smoke-test`: запуск точки входа приложения без соединения со службами.

Используется стандартный ARM64 runner `macos-26` с явно выбранным Xcode 26.6. Доступность версии определяется [образом GitHub](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md); при его обновлении может понадобиться изменить `DEVELOPER_DIR`. Локально проект также проверялся с Xcode 27.0. Проверка в CI не подтверждает поддержку всех Mac и версий macOS.

Workflow имеет только `contents: read`, не требует пользовательских секретов и не сохраняет Git-учётные данные в checkout. Сторонние actions закреплены полными SHA. Новый прогон того же PR или ветки отменяет предыдущий; предел выполнения — 20 минут. Скрипты не устанавливают службы и не меняют питание runner.

Архивы `.app` в Actions больше не сохраняются. Сборка остаётся обязательной проверкой: она выявляет ошибки упаковки, подписей и установочного содержимого. DMG и черновик GitHub Release создаёт отдельный workflow `Release` только по тегу версии. Промежуточный артефакт в этом workflow используется для передачи проверенного DMG между jobs; обычный CI ничего не сохраняет.

Зелёный CI подтверждает автоматические проверки. Физическая крышка, реальные отказы установленных служб и энергия остаются отдельными [аппаратными испытаниями](validation.md). Обязательность проверки перед merge настраивается отдельно в правилах защиты `main`.

## Версии и выпуски

Единственный источник версии приложения — `Resources/Info.plist`:

- `CFBundleShortVersionString` — версия продукта `MAJOR.MINOR.PATCH`, например `0.1.1`.
- `CFBundleVersion` — положительный целый номер сборки, например `2`. Перед распространением новой сборки увеличиваем его; при смене версии продукта не обнуляем.

Скрипт сборки копирует эти значения в bundle без автоматического увеличения. Обычные локальные пересборки и прогоны CI номер не меняют. Версия в ветке обозначает готовящийся выпуск, а не факт его публикации. Перед передачей пользователям изменённого кандидата увеличиваем номер сборки, даже если версия продукта остаётся прежней.

Используем [SemVer](https://semver.org/lang/ru/) как основу соглашения. Для приложения совместимость означает сохранение документированных сценариев, пользовательских данных/настроек и поддерживаемых платформ:

- **PATCH** (`0.1.0 → 0.1.1`, после стабилизации `1.2.0 → 1.2.1`): совместимые исправления ошибок, безопасности и небольшие улучшения без новой функции. Исправление ложного предупреждения при открытии меню — patch.
- **MINOR** (`1.2.1 → 1.3.0`): новые совместимые возможности, например дополнительный режим таймера. PATCH сбрасывается в ноль.
- **MAJOR** (`1.3.2 → 2.0.0`): несовместимое изменение документированного поведения, потеря поддержки платформы или изменение данных, требующее ручной миграции. MINOR и PATCH сбрасываются в ноль. Размер diff или новый дизайн сами по себе не определяют major.

Пока проект в `0.x`, стабильность не обещается. Наше соглашение для этой стадии: исправления идут в `0.x.y`, новые возможности и несовместимые изменения — в следующую `0.x.0`; несовместимости обязательно описываются в журнале. Переход на `1.0.0` — отдельное решение о готовности поддерживать стабильное поведение, после проверки основных сценариев и обновления приложения. Это не автоматический результат количества PR.

Версия IPC (`ServiceProtocol.version`) независима от версии приложения. Меняем её при несовместимом изменении обмена со службами, а не при каждом исправлении UI. Повторная настройка доверия после изменения подписи — обычный процесс обновления проекта и сама по себе не требует major.

### Что делать в PR

1. Описать влияние на пользователя в `CHANGELOG.md`, в разделе готовящегося выпуска. Изменения только документации, тестов, CI или внутренний рефакторинг без изменения поведения обычно не требуют новой версии продукта.
2. В шаблоне PR указать `patch`, `minor`, `major` или «без выпуска» и причину. При нескольких изменениях выбираем самый высокий необходимый уровень.
3. При подготовке выпуска согласованно изменить оба поля в `Info.plist` и заголовок готовящейся версии в журнале. Несколько PR могут войти в один выпуск; повышать версию на каждый PR не нужно.
4. Запустить безопасные тесты, собрать bundle и проверить фактические значения версии. Обновление установленного приложения проверяется отдельно.

Решение о типе изменения проверяет человек при ревью. Шаблон PR напоминает об этом; текущий CI **не определяет SemVer и не повышает версию автоматически**. Название коммита `fix:`/`feat:` помогает читать историю, но не заменяет оценку совместимости.

### Команда подготовки выпуска

Для локальной `main`, когда разрешён прямой push в эту ветку:

```sh
./scripts/prepare-release.py 0.1.2 --dry-run
./scripts/prepare-release.py 0.1.2
```

`0.1.2` — пример, а не автоматически выбранная следующая версия. Команда:

1. Требует чистый checkout на `main`, включая отсутствие незакоммиченных и неотслеживаемых файлов. Проверяет наличие локального и удалённого тега, доступность `origin` и то, что текущая `main` содержит актуальный коммит удалённой `main`. Читает remote, но ничего туда не отправляет.
2. Проверяет формат `MAJOR.MINOR.PATCH` и запрещает понижение версии. Можно финализировать уже указанную в исходниках версию, если тег ещё не существует.
3. Обновляет `CFBundleShortVersionString`, увеличивает целочисленный `CFBundleVersion` на единицу. Пересборки эту команду не вызывают.
4. Берёт первый раздел `CHANGELOG.md` с заголовком `## <текущая версия> — готовится`, сохраняет описание изменений, обновляет его версию и ставит дату подготовки. Заметки нужно написать заранее; команда их не сочиняет. Также обновляет существующую строку «Кандидат: версия …, сборка …».
5. Создаёт локальный коммит только с `Info.plist` и журналом, затем аннотированный тег `vX.Y.Z` на этот коммит. Использует обычные настройки Git для hooks и подписи коммитов/тегов.

`--dry-run` выполняет предварительные проверки без изменения файлов, коммитов и тегов. `--date YYYY-MM-DD` задаёт дату подготовки; по умолчанию используется локальная календарная дата. Дата фактической публикации фиксируется GitHub Release. Если Git hook, подпись коммита или создание тега завершаются ошибкой, скрипт останавливается и сообщает, что проверить: локальные изменения или коммит могут остаться, автоматического отката нет.

Отправка остаётся отдельным осознанным действием:

```sh
git push --atomic origin main v0.1.2
```

Если `main` принимает изменения только через PR, автоматическая подготовка коммита и тега одним вызовом не подходит: изменение версии и журнала проходит PR, а тег ставится на итоговый коммит после merge и проверок. Скрипт не обходит правила GitHub. Он не запускает тесты приложения, не собирает DMG и не публикует выпуск.

### Workflow выпуска по тегу

[`.github/workflows/release.yml`](../.github/workflows/release.yml) запускается только при push тега, начинающегося с `v`; валидатор принимает строго `vMAJOR.MINOR.PATCH`. Предрелизные суффиксы пока не поддерживаются. Workflow должен уже присутствовать в помеченном коммите. Два последовательных job:

1. **Test and package DMG (macOS ARM64)** — `macos-26`, Xcode 26.6, `contents: read`, до 30 минут. Checkout конкретного SHA события, проверка совпадения коммита тега и принадлежности истории `origin/main`. Затем совпадение тега с `Info.plist`, корректность номера сборки, датированный непустой раздел журнала, полный безопасный набор тестов и сборка приложения. Повторная проверка версии внутри `.app`, подготовка release notes и DMG.
2. **Create GitHub Release draft** — Ubuntu, `contents: write`, до 10 минут. Получает только файлы выпуска из успешного первого job, проверяет неизменность тега и контрольную сумму DMG, создаёт **черновик** через `gh release create --draft --verify-tag`. В описании — изменения выбранной версии и инструкция первого запуска. Во вложениях — `DontSleep-macos-arm64.dmg` и `SHA256SUMS`. Ссылка появляется в итогах запуска Actions.

Используется локальная ad-hoc подпись. **Платная подпись Developer ID и нотарификация Apple не выполняются; Apple-аккаунт и секреты сертификатов не нужны.** Для записи черновика используется встроенный `GITHUB_TOKEN`. Все actions закреплены точными SHA; checkout не сохраняет credentials. Автопубликации нет.

Готовые файлы передаются между jobs через артефакт, сохраняемый на 7 дней. Второй job получает его по ID, поэтому повтор только неудавшегося job может использовать первоначальный артефакт в пределах этого срока. Повтор всех jobs создаёт новый артефакт. Релизы в GitHub Releases не имеют этого срока хранения.

Параллельные выпуски одного тега сериализованы, выполняющийся выпуск не отменяется новым. Любой уже существующий релиз с тем же тегом, включая черновик, останавливает создание: скрипт не перезаписывает вложения и не публикует черновик. Если загрузка оборвалась, сначала осмотрите неполный черновик; для повторного создания удалите только этот черновик и повторите неудавшийся job. Опубликованный выпуск не заменяйте — исправления идут под новым тегом.

Если отправить ветку и тег одним push, обычный CI и Release могут идти одновременно. Поэтому Release выполняет собственные обязательные проверки и не полагается на порядок завершения другого workflow.

### Локальная проверка DMG

```sh
./scripts/setup-dmg-tools.sh  # первый запуск / после изменения requirements-dmg.txt
./scripts/build-app.sh
./scripts/build-dmg.py
```

Результат — `dist/release/DontSleep-macos-arm64.dmg` и `dist/release/SHA256SUMS`. Упаковщик принимает `--app /absolute/path/to/app` и `--output /output/directory`. Он проверяет совпадение версии и номера сборки с исходным `Info.plist`, подписи и ARM64 у всех трёх бинарников; копирует `.app`, ссылку `/Applications` и `Установка.txt` из `docs/installation.txt` в HFS+ образ. На временно подключённом записываемом томе создаёт оформление Finder, затем отключает том и сжимает его в UDZO. После этого проверяет образ, повторно подключает его только для чтения, проверяет содержимое, оформление, подписи и безопасный `--smoke-test`, отключает образ и вычисляет SHA-256. Установка служб не выполняется. При неудаче отключения временный каталог сохраняется для диагностики.

#### Оформление образа

- Окно 720×460: Applications слева, приложение справа, два тонких чёрных шеврона влево; внизу настоящий `Установка.txt` с отдельной иконкой. Иконки можно перетаскивать и открывать.
- `scripts/render-dmg.swift` отрисовывает светлый фон с рамкой и мягкой тенью через AppKit. В TIFF объединяются варианты 1× и 2×; текст, рамка и шевроны являются частью фона, сами файлы рисует Finder. Фон фиксированный светлый и не меняется с темой системы. Цвет папки и другие системные детали зависят от macOS.
- `Resources/DMG/VolumeIcon.png` — согласованная иконка глаза над диском. Из неё собирается ICNS для подключённого тома. Иконка самого приложения не меняется. У скачанного через HTTP файла `.dmg` Finder может показать стандартный значок; кастомная иконка тома находится внутри образа и сохраняется при скачивании.
- `scripts/dmg_layout.py` записывает `.DS_Store` без AppleScript и управления Finder. Alias фона создаётся именно на HFS+ томе, чтобы он сохранялся после переноса/скачивания образа. Повторное подключение проверяет координаты, флаги иконок, содержимое ресурсов и ссылку на фон.
- `scripts/setup-dmg-tools.sh` устанавливает `ds-store` и `mac-alias` только в `.build/dmg-tools`, с фиксированными версиями и SHA-256 из `scripts/requirements-dmg.txt`. Нужна сеть при первой установке; в приложение эти зависимости не входят. Версии совместимы с системным Python 3.9.
- `dist/release/layout-preview.png` — техническое превью из renderer, а не снимок живого Finder. Оно не включается в релиз. Окончательный вид и поведение проверяются открытием готового DMG в Finder.

Проверить метаданные конкретного будущего выпуска и подготовить его описание можно так (номер — пример):

```sh
./scripts/release_metadata.py v0.1.2 \
  --app "$PWD/dist/Don’t Sleep.app" \
  --notes-output dist/release/release-notes.md
```

В отличие от локальной упаковки DMG, валидатор релиза требует, чтобы первый раздел `CHANGELOG.md` уже имел дату подготовки вместо «готовится».

### Когда выпуск считается опубликованным

Локальный тег, его отправка и дата подготовки в журнале сами по себе не означают публикацию. Выпуск опубликован, когда доступен GitHub Release с проверенным приложением. После успешного Release скачайте DMG из черновика через браузер, проверьте установку, разрешение первого запуска в macOS, настройку служб и изменённые сценарии. Затем откройте черновик в GitHub Releases и нажмите **Publish release**. Локальная проверка образа не воспроизводит Gatekeeper для скачанного файла и не заменяет аппаратную проверку. Merge PR сам по себе не создаёт выпуск.

Не передвигаем опубликованный тег и не заменяем его приложение изменённым содержимым. Исправления опубликованной версии выпускаются под новым номером.

Правила полей bundle: [версия продукта](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring) и [номер сборки](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion). Предрелизные суффиксы вроде `-beta.1` не записываем в `CFBundleShortVersionString`; статус кандидата отмечаем в журнале и описании выпуска.

## Сборка приложения

```sh
./scripts/build-app.sh
```

По умолчанию — release. Для отладочного bundle:

```sh
DONT_SLEEP_BUILD_CONFIGURATION=debug ./scripts/build-app.sh
```

Результат — `dist/Don’t Sleep.app`. Прежний bundle переносится в `dist/.previous/`. Скрипт проверяет SHA-256 установщика, собирает три бинарника, копирует ресурсы, подписывает их ad-hoc и вызывает проверку bundle. Он не регистрирует службы и не меняет питание.

Повторная проверка готовой сборки:

```sh
./scripts/verify-bundle.sh "$PWD/dist/Don’t Sleep.app"
'dist/Don’t Sleep.app/Contents/MacOS/DontSleepApp' --smoke-test
```

`verify-bundle.sh` принимает абсолютный путь; проверяет подписи, идентификаторы, ресурсы и выполняет `--verify-installation-payload` без установки, подключения к службам и системного запроса администратора. Проверки bundle не заменяют тесты кода и аппаратные испытания.

Не обновляйте `InstallerProgram.pinnedSHA256` механически: изменение установщика требует ревью соответствующих привилегированных операций, после чего согласованно обновляются скрипт и его pin. После изменения подписанного кода установленная конфигурация доверия требует повторной настройки через UI.

## Изображения интерфейса и иконка

Готовый бинарник умеет отрисовывать состояния окна из фиксированных данных:

```sh
'dist/Don’t Sleep.app/Contents/MacOS/DontSleepApp' --render-previews "$PWD/dist/previews"
```

Команда создаёт 20 PNG (10 состояний × 2 темы), без клиента служб и изменения питания. Это иллюстрации окна на тестовых данных, не снимки текущего состояния Mac и не изображение верхнего NSMenu. После визуальной проверки в Git можно оставить только нужные изображения в `docs/images/`. В текущем внеэкранном экспорте системные материалы и акцентные цвета могут отличаться от живого окна; тёмный экспорт также показал некорректный цвет части текста. Не используйте эти снимки как доказательство правильности живого оформления или доступности. Для README выбраны только два проверенных светлых состояния.

Для отдельного экспорта иконки из нативного рисунка:

```sh
'dist/Don’t Sleep.app/Contents/MacOS/DontSleepApp' --export-icon "$PWD/dist/icon-export"
```

Получаются PNG, iconset и ICNS; сборка использует закоммиченный `Resources/Assets/AppIcon.icns`. Экспорт в `dist` не заменяет исходные ресурсы автоматически.

## Перед изменением документации

Сверяйте поведение с `AppModel`, `Presentation`, `SessionEngine`, `ServiceMessages` и скриптами. В [статусе проверки](validation.md) отделяйте свежие автоматические результаты, сообщение пользователя и ещё не выполненные аппаратные сценарии. Не выдавайте старые хеши bundle или число тестов за текущие. Правила состава Git описаны [отдельно](repository.md).
